# V2 實作設計與驗收

## 目標

Telegram Canonical Bridge 不是另一個 Telegram agent。它讓受控 Telegram 私訊進入 Hermes Controller 既有的 canonical `Bot Chat`，保留 Bot Mode 與原生 `message_agent`，並補上非同步派工缺少的可觀察性與耐久留言。

V2 的完成條件：

1. 不建立 `agent:main:telegram:*` 一般平台 session。
2. 不修改 Hermes core、不覆寫 `message_agent`。
3. 只有已綁定 canonical Bot Chat 及其子任務會被追蹤。
4. 任務狀態必須有 hook、工具回報、event replay 或 process table 等可指認證據。
5. Telegram 使用者可留言給進行中的任務，但不虛構成即時中斷。
6. Controller 與 named profiles 共用同一份耐久 ledger。
7. Hermes 或 Telegram 短暫離線時可恢復，不盲目重送可能已執行的 prompt。

## 核心語意

### Controller session

一般 Telegram adapter 會依訊息來源建立平台 session；本外掛刻意不呼叫 `BasePlatformAdapter.handle_message()`。輸入會透過 backend RPC 提交到目標 profile 的 canonical session，所以 Telegram 與 Desktop 看到的是同一個 Controller 對話脈絡。

### Worker session

原生 `message_agent` 是 fire-and-forget：本機訊息會送進目標 OT 自己的 canonical `Bot Chat`，每次呼叫則建立新的背景 turn 與 process handle。這不是一條可持續插話的雙向連線。V2 在 OT turn 啟動時綁定其 session／turn ID；canonical 對話可延續，但 resolved runtime ID 仍可能因 compaction 或重啟輪替。

### 壓縮

Hermes 仍是對話上下文與 compaction 的唯一權威。外掛保存 canonical root/runtime binding，binding 過期時才重新 `session.resume`；不攔截、不重作，也不阻止 Hermes 壓縮。

SQLite ledger 只保存任務協調資料與必要時清理後的 OT final assistant response，不會被對話 compaction 刪除。它不保存 chain-of-thought、conversation history 或原始工具資料，也不能代替 Hermes session history。

## 元件

| 元件 | 責任 | Hermes 相依邊界 |
| --- | --- | --- |
| `adapter.py` | platform lifecycle、Telegram polling、指令、editable task card、outbox | `BasePlatformAdapter`、platform registry、scoped lock |
| `tools.py` | eager tools/hooks 入口 | plugin tool discovery |
| `task_features.py` | `message_agent` marker、worker binding、進度／inbox tools、hook observers | plugin hooks 與 `register_tool` |
| `task_model.py` | task ID、狀態、final 摘要清理與 Telegram 呈現 | 無 |
| `service.py` | canonical prompt、history、event replay、process polling | Hermes backend JSON-RPC |
| `state.py` | inbound、outbox、binding、task/event/note ledger | SQLite |
| `telegram_api.py` | 最小 Bot API：poll、send、edit、typing | Telegram HTTPS API |
| `config.py` | fail-closed 設定、scoped secrets、machine-root ledger 路徑 | 集中處理 Hermes helper |

根 plugin 是 import-light 的。Controller 啟用 platform 時才初始化 Telegram adapter；OT profile 載入 tools/hooks 時不需要 Telegram token。

## 派工資料流

```text
Controller pre_tool_call(message_agent)
  ├─ 確認 session 是已綁定 canonical，或正在執行的 parent task
  ├─ 建立 bridge_tasks row 與第一版狀態卡 outbox
  └─ 在 message 前置 [TCB-TASK:TCB-YYYYMMDD-XXXXXX]

native message_agent
  ├─ post_tool_call 讀 sent/process_id
  └─ event replay 作為 ack 補抓

OT pre_llm_call
  ├─ 從 marker 找 task
  ├─ 綁定 worker profile/session/turn
  └─ 注入進度回報與 inbox 檢查規則

OT turn
  ├─ pre/post tool hooks：記錄高階、可觀察活動
  ├─ bridge_task_update：OT 明確回報可驗證里程碑；最終里程碑使用 status=result
  └─ bridge_task_inbox：讀取 Telegram durable notes

OT post_llm_call → 保留明確進度，否則保存清理／截短後 final → returning
agents.list exited + hook evidence → completed / finished
Telegram editable task card → 耐久呈現 OT 結果
Controller session.history → Controller 自己的回覆 durable outbox → Telegram
```

marker 是 task correlation ID，不是授權憑證。`bridge_task_update` 與 `bridge_task_inbox` 仍會檢查呼叫者 session 是否已綁定該任務。

## 任務狀態機

```text
dispatching → dispatched → running ⇄ waiting / blocked → returning → completed
      ├──────────────── 缺少 final／exit code 證據 ───────────────→ finished
      └────────────────────────────── failure paths ───────────────→ failed
```

| 狀態 | 寫入來源 | 可信範圍 |
| --- | --- | --- |
| `dispatching` | Controller `pre_tool_call` | 只證明派工 intent 已建立 |
| `dispatched` | `message_agent` ack | 只證明 Hermes 建立背景程序 |
| `running` | OT `pre_llm_call`、`agents.list`、工具 activity | 只證明 turn／程序／工具活動存在 |
| `waiting` | OT `bridge_task_update` | OT 表示在等外部條件或留言 |
| `blocked` | OT 回報或 session interrupted | 工作需要介入；不代表自動重派 |
| `returning` | OT `post_llm_call` | 最終答覆已產生、任務卡更新已排隊；不宣稱 Controller 已收到原生通知 |
| `completed` | `post_llm_call` 後觀察到 exited，或經 grace 後 handle 已不在全域摘要；也可由 exit code 0 證明 | worker final 已產生且背景程序不再活動，不保證原生通知送達或內容正確 |
| `finished` | 只觀察到 exited，沒有 final hook 或 exit code | 程序已停止，bridge 無法判定結果 |
| `failed` | dispatch error、worker failure、非零 exit | 有明確失敗證據 |

終態不會被較晚的 polling 降級。每次 transition 都增加 revision、保存 event，並把尚未送出的狀態卡 revision 合併成一筆 outbox。

OT 透過 `bridge_task_update` 寫入的明確里程碑，優先於後續泛用 tool category；完成 transition 只更新狀態與證據，不抹掉最後一筆有價值的進度。這可避免「已確認頁面標題」在關閉 browser 後退化成「正在執行本機程序」。最終明確里程碑使用 `status=result`，它優先於 final fallback；若只有較早的一般進度或完全沒有明確回報，`post_llm_call` 的 `assistant_response` 會經 marker 移除、空白正規化與長度限制後成為保底結果。

## Telegram 任務卡與留言

每個 task 原則上只建立一張 Telegram 訊息；後續 revision 使用 `editMessageText`。若卡片已刪除或 Telegram 表示不可編輯，bridge 解除舊 message ID 並建立新卡。`message is not modified` 視為成功。

留言有兩個入口：

- `/tell <task_id> <內容>`
- 回覆該任務卡

留言先寫入 `bridge_task_notes`，再顯示為待讀。OT 必須呼叫 `bridge_task_inbox` 才會收到；讀取可原子標記為 `read`。OT 進入 `returning` 或終態時，仍為 `unread` 的留言會原子標成 `missed`、從卡片待讀數移除，並透過 durable notice 告知使用者內容未納入本次結果。終態任務拒絕追加留言，避免使用者誤以為舊 process 還能收到新需求；啟動 reconciliation 也會處理舊版遺留的 closed-task unread notes。

這套 inbox 是 checkpoint delivery，不是 live interrupt。若要做到真正的即時控制，需要 Hermes 提供對 running background turn 的官方 input/inject/cancel RPC；V2 不以不穩定內部 hack 模擬。`missed` 警告是對競態的誠實結案，不代表該留言曾送進 OT context。

## SQLite 資料模型

| Table | 用途 |
| --- | --- |
| `inbound` | Telegram update 去重、提交狀態與 retry lease |
| `active_routes` | Controller profile 對 Telegram chat/user 的單一綁定 |
| `canonical_bindings` | canonical root ID 與目前 runtime ID |
| `canonical_seen` | assistant history 去重 |
| `outbox` | 一般回覆、notice 與 task card 的 durable delivery |
| `bridge_tasks` | 任務目前快照、origin/worker/process correlation |
| `bridge_task_events` | 每次 task revision 的稽核事件 |
| `bridge_task_notes` | Telegram 給 OT 的未讀／已讀留言 |
| `meta` | Telegram offset、history bootstrap、event cursor/epoch |

Controller 與 OT 都用短生命週期連線、WAL、foreign keys、busy timeout 與 `BEGIN IMMEDIATE`。V1 DB 啟動時會原地新增 `outbox.task_id`；多個 profile 同時首次 migration 時，duplicate-column race 視為同伴已完成。

預設路徑使用 Hermes machine root，而不是 named profile 的個別 home：

```text
<HERMES_ROOT>/plugin-data/telegram-canonical-bridge/bridge.sqlite3
```

## Canonical 輸入與歷史回覆

### 輸入

1. Telegram `getUpdates`。
2. 檢查 private chat、allowlist、選填 `home_chat_id`。
3. `inbound` 先落地並以 `update_id`、chat/message ID 去重。
4. `profiles.list` 找指定 profile 的 canonical session。
5. 必要時 `session.resume`，再 `prompt.submit(queued=true)`。

`prompt.submit` 是非冪等操作。若 bytes 送出後連線中斷、無法判定 backend 是否接受，該 inbound 會標記 `uncertain` 而不自動重送。

### Controller 回覆

`session.history` 是 Controller assistant 文字的恢復來源。首次看到一個 canonical root 時只建立 baseline，不回放舊對話；之後以 row key 與 digest 去重，新回覆先寫 outbox，再送 Telegram。長文字依 Telegram UTF-16 限制切段。

原生 `message_agent` 的背景完成通知仍由 Hermes 管理；短生命週期 RPC watcher 不保證當下存在可被喚醒的 live session owner。因此 V2 不把「OT 最終文字一定先回到 Controller」當成交付保證。對已追蹤任務，優先顯示 OT 的明確 `bridge_task_update`；若不存在，則由 OT `post_llm_call` 的清理後 final assistant response 補到同一張任務卡。Controller 若之後收到原生通知並回覆，仍會由上述 history 路徑傳到 Telegram。

## Telemetry

V2 使用兩條唯讀補抓路徑：

- `session.events.since`：讀 bounded event ring，補抓 `message_agent` tool completion。保存 cursor 與 epoch；epoch 改變時從 ring 起點重播。
- `agents.list`：以全域、唯讀摘要依 process handle 觀察 running/exited。它不需要附著 live session；目前 Hermes 摘要不保證提供 exit code，且完成或 backend 重啟後 row 可能直接消失。

這兩條路徑不呼叫 `session.resume`，避免 watcher 改變 session 擁有權。`process.list` 在 Hermes 0.21 是 live-session scoped，不適合短生命週期 watcher，因此不使用。事件 ring 可能 truncate，且全域 process 摘要可能沒有 exit code；若任務已有 `post_llm_call` final 證據，handle 又連續超過 grace 不在 `agents.list`，V2 以 `absent after grace` 結案，避免永久停在 `returning`，但不宣稱 Controller 收到原生通知。OT 結果由明確進度或 final hook 保底，Controller 回覆則由持久 history 回收。

## 安全邊界

- `allowed_user_ids` 必填且不可為空；只接受 private chat。
- Bot token 與 backend token 只從 Hermes scoped secret／環境讀取。
- `backend_url` 禁止 `token=` query；credential 只在記憶體中附加 handshake。
- 相同 bot token 以雜湊 identity 取得 platform lock，防止同一 gateway 內重複 polling。
- 建議 backend 只綁 loopback；跨機器請先使用受保護 tunnel。
- task card 只顯示清理後的狀態摘要，以及必要時截短的 final assistant response；不保存 conversation history、原始 tool args/result 或私密思考。這份 final 視為可向發起該任務的 allowlisted Telegram 使用者公開。
- hook observer 失敗時 fail-open，避免破壞原生派工；log 會留下追蹤缺口。

## 相容性策略

外掛以正式 plugin manifest、root `register(ctx)`、tools、hooks 與 platform adapter 組裝；沒有修改 Hermes 套件檔案。Hermes-specific import 集中在 adapter/config/registration 邊界，RPC 名稱集中於 `service.py` 與 `hermes_rpc.py`。

每次 Hermes 升級或 plugin 更新後執行：

```powershell
python -m unittest discover -s tests -v
hermes plugins doctor --ci <plugin-path>
hermes plugins compat <plugin-path>
```

若 hooks 或 RPC shape 改變，原生 `message_agent` 應保持可用，但 task telemetry 可能降級；doctor、compat 與垂直驗收用來提早發現這類變更。

## 驗收矩陣

### 靜態與單元測試

1. `compileall` 成功。
2. SQLite V1 migration、inbound/outbox 去重、task lifecycle、durable inbox 測試通過。
3. canonical history、uncertain submit、event replay、process polling 測試通過。
4. hook marker、worker authorization、無 route 與無關 session 不改寫測試通過。
5. Controller 與 OT profile 解析到相同 shared state path。
6. plugin doctor 顯示 3 tools、5 hooks；compat 無 deprecated import。

### 本機垂直驗收

1. Controller 與每個 OT profile 都已安裝並 enable plugin/toolset。
2. Controller platform 有秘密、allowlist 與 canonical profile 設定。
3. `hermes serve` 在 `127.0.0.1:9119` 可達，gateway healthy。
4. Telegram 一般文字出現在既有 canonical Bot Chat，而非新 Telegram session。
5. Controller 呼叫 `message_agent` 後建立 task card 與 process handle。
6. OT turn 綁定 task，能讀 inbox 並回報明確里程碑。
7. `process running` 不被誤報成 browser 已開啟；只有工具成功後才可明確回報。
8. OT 明確進度優先保留；沒有明確進度時，清理後 final assistant response 出現在完成任務卡。
9. Hermes 原生通知若喚醒 Controller，Controller 回覆另由 canonical history 傳回 Telegram。
10. gateway 重啟後 pending outbox 可續送，不重送 submitted/uncertain prompt。

## 已知範圍

- V2 僅支援一個 private chat 對一個 Controller profile。
- 僅處理文字；媒體需要額外的落地、大小、掃描與權限設計。
- 沒有 token streaming，也沒有 worker live screen。
- durable note 延遲取決於 OT 的 checkpoint；長時間單一工具呼叫期間無法即時讀取。
- 沒有自動重派 interrupted task，以免重複造成外部副作用。
