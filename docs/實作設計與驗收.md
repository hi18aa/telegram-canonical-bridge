# v0.5 實作設計與驗收

## 1. 設計決策

v0.5 採用「原生 Telegram＋Agent task sidecar」：

```text
Telegram 使用者
    ↕ Hermes 原生 Telegram adapter
Controller session
    ↕ agent_task_start/status/message/cancel
Bridge task ledger + runner
    ↕ hermes -p <worker> chat -c "Bot Chat"
Worker canonical Bot Chat
    ↕ bridge_task_update/inbox/status + hooks
Bridge task ledger
    ↘ hermes send → Telegram 任務時間線
```

原生 adapter 是使用者訊息、附件、命令、streaming 與 typing 的唯一擁有者。sidecar 不輪詢 Telegram、不持有 token，也不建立第二個 user-facing session。

## 2. Hermes 相依邊界

| 能力 | 使用方式 | 升級風險控制 |
| --- | --- | --- |
| Plugin 註冊 | manifest、root `register(ctx)` | `plugins doctor` |
| Tools／hooks | `register_tool`、`register_hook` | 單元測試與真實 turn |
| 主 Agent system prompt | `register_system_prompt_section` | session smoke test |
| Worker turn | 公開 `hermes -p ... chat -c "Bot Chat" --create-if-missing -Q --query-file` | runner E2E |
| Telegram outbound | 公開 `hermes send --to ... --file ... --quiet` | outbox E2E |
| 背景執行 | 內建 `terminal(background=true, notify=true)` | process ID correlation |
| 取消 | 內建 `process_manage(action=kill)` | tree-kill E2E |

外掛不寫入 Hermes conversation database、不 import Desktop UI state、不覆寫 `message_agent`。

## 3. 元件

| 檔案 | 責任 |
| --- | --- |
| `tools.py` | 註冊 controller／worker tools 與 hooks |
| `agent_tasks.py` | roster、system prompt、start/status/message/cancel、slash command |
| `agent_task_runner.py` | profile 驗證、同 Bot file lock、公開 Hermes CLI invocation、payload 清理 |
| `task_features.py` | worker marker binding、進度／inbox tools、LLM/tool/completion observers |
| `task_model.py` | task ID、狀態標籤、進度清理與時間線文字 |
| `state.py` | SQLite task/event/note/outbox、冪等與 transition |
| `native_delivery.py` | `hermes send` 封裝、outbox claim/send/defer、背景 runner kick |
| `native_delivery_runner.py` | 短生命週期 retry loop 與跨程序 delivery lock |
| `adapter.py` | v0.4 自管 Telegram adapter，相容保留；v0.5 推薦模式停用 |

## 4. Controller 派工流程

1. `pre_tool_call(agent_task_start)` 以來源 session ID＋tool call ID 建立冪等 intent。
2. 驗證 `controller_profiles`、Bot roster、profile existence、訊息長度與附件。
3. 任務文字寫入 mode 0600 暫存檔；command line 只放路徑與 opaque task ID。
4. `terminal` 以 background＋notify 啟動 `agent_task_runner.py`。
5. runner 取得目標 profile 專屬 file lock。
6. runner 呼叫公開 Hermes CLI，開啟或沿用目標 canonical `Bot Chat`。
7. `agent_task_start` 取得 process ID 後回覆 `sent`，不等待 worker 完成。
8. Hermes completion notification 依 process ID 回填 exit code 與可辨識 final reply。

若相同 tool call 因模型或 host retry 重入，既有 task/process 直接回傳，不建立第二個 runner。

## 5. Worker 綁定與結果

派工 payload 含 `[TCB-TASK:TCB-...]` marker。worker 的 `pre_llm_call` 讀取 marker，並綁定：

- worker profile
- worker session ID
- worker turn ID

之後 worker 才能使用 `bridge_task_update`、`bridge_task_inbox` 與 `bridge_task_status`。單有 runner process 不會被誤認成 worker 已啟動。

結果優先順序：

1. `bridge_task_update(status="result")` 的明確結果。
2. `post_llm_call` 的清理後 final assistant response。
3. Hermes completion notification 中可辨識的 worker reply。

任何來源都不保存 chain-of-thought、原始 tool arguments 或完整 conversation history。

## 6. 任務狀態機

```text
dispatching → dispatched → running ⇄ waiting / blocked
       │            │          │
       │            │          └→ returning → completed
       │            ├────────────→ failed
       │            └────────────→ unconfirmed
       └─────────────────────────→ failed

dispatching/dispatched/running/waiting/blocked
       └─ explicit cancel → stopping → cancelled | unconfirmed
```

規則：

- `sent` 只會到 `dispatched`。
- worker `pre_llm_call` 才能提供 `running` 證據。
- final 與 exit 0 必須交叉確認才到 `completed`。
- 非零 exit 提供 `failed` 證據，但不自動重派。
- 缺證據使用 `unconfirmed`，不是成功終態。
- `completed`、`failed`、`cancelled` 等確定終態不被較晚的弱 telemetry 降級。
- `unconfirmed` 可被較晚抵達的強證據恢復。

## 7. 補充訊息與取消

`agent_task_message` 寫入 `bridge_task_notes`，不注入 running turn。worker 必須在檢查點呼叫 `bridge_task_inbox`；讀取會原子改為 `read`。final 後仍未讀的 note 會改為 `missed`，不假裝已被採用。

`agent_task_cancel` 只接受建立 task 的 Controller profile：

1. transition `stopping`。
2. `process_manage kill` 指向 task process ID。
3. Hermes 確認 killed 後 transition `cancelled`，exit code 記為 `-15`。
4. 找不到或無法確認 handle 時 transition `unconfirmed`。

外部網站已執行的副作用不在程序取消的回滾範圍。

## 8. Session 與 concurrency

`agent_task_runner` 對 profile 名稱計算 SHA-256 lock filename。同一 profile 的 runner 依序取得鎖；不同 profiles 使用不同 lock。

因此：

- 同一 Bot 的多項任務不會同時寫 canonical conversation。
- 第二項任務可以先建立 process／task，但會等待前一項釋放 lock。
- 不同 Bots 可並行。
- 多個 Controllers 呼叫同一 Bot 時共享 canonical history，但 origin profile 與 task IDs 分開記錄。

Hermes 自己負責 canonical compaction。runtime/session 細節可輪替，但 Bot Chat 邏輯名稱與 task marker 仍可重新關聯。

## 9. 附件

`agent_task_start.attachments` 只接受同機既有一般檔案：

- 最多 10 個。
- 總計最多 128 MiB。
- 預設複製到共用 plugin-data 下的 task 目錄。
- 檔名正規化，worker 收到絕對路徑。
- 任務內容與檔案 bytes 不進入 process command line。

Telegram upload/download 仍由原生 adapter 負責；sidecar 不實作媒體協定。

## 10. Native delivery 與重試

task transition 先寫 `bridge_task_events` 與 outbox，再喚醒 delivery runner。Agent hook 不同步等待 `hermes send`。

同一 task 的 claim 查詢只允許最早未送事件，確保順序。每次成功後重新 claim，讓快速產生的 `result → returning → completed` 能在同一輪排空。

傳送失敗時使用 bounded exponential retry。delivery runner 會觀察 `next_attempt_at` 與 sending lease，最長運作 10 分鐘；outbox 清空後經短 idle grace 自行退出。多個 kick 由 file lock 合併，不會同時重複傳送。

## 11. SQLite 資料

主要 tables：

| Table | 用途 |
| --- | --- |
| `bridge_tasks` | 任務快照、origin、worker、process、exit code |
| `bridge_task_events` | 每次 transition 與 evidence 稽核 |
| `bridge_task_notes` | unread／read／missed 補充指示 |
| `outbox` | Telegram 任務時間線、lease、retry 與 delivery ID |

v0.4 的 inbound、canonical binding 等 tables 為舊 adapter 相容保留。v0.5 sidecar 不用它們接管原生 Telegram。

預設路徑：

```text
<HERMES_ROOT>/plugin-data/telegram-canonical-bridge/bridge.sqlite3
```

## 12. 安全邊界

- 明確 controller allowlist 與 worker roster。
- profile 名稱只允許 `[A-Za-z0-9_-]` 且限制長度。
- delivery target 經格式驗證。
- 任務內容以暫存檔交付，完成後刪除。
- task 控制操作檢查 origin profile。
- hook observer fail-open，不阻斷 Hermes core；狀態可能降級為 `unconfirmed`。
- SQLite、附件目錄與 event spool 都視為敏感本機資料。
- legacy adapter 與 native Telegram 不應同時輪詢相同 token。

## 13. Hermes `Unknown toolsets` 問題

Hermes 0.21.0 的 CLI 可能在背景 plugin discovery 完成前驗證持久化 plugin toolset，先輸出：

```text
Warning: Unknown toolsets: telegram_canonical_bridge
```

後續正式 tool discovery 仍會載入工具與 hooks。此競態已以真實 worker turn 證明並非執行失敗。runner 只過濾名稱集合完全屬於本外掛的該行，其他 unknown toolset 警告原樣保留；外掛不修改 Hermes core。

## 14. 自動測試

目前測試涵蓋：

- SQLite migration、state transition、event order 與 note reconciliation。
- start 冪等、roster validation、payload 不出現在 command line。
- `sent`／worker start／explicit result／final／completion correlation。
- message 不隱式中斷。
- cancel 使用 `process_manage` 並轉為 `cancelled`。
- native／legacy outbox 分流。
- `hermes send` 使用 task origin profile。
- 單次 flush 排空同 task 多事件。
- async delivery kick、deferred retry 與 runner 自動退出。
- 只過濾本外掛已知的 startup false-positive warning。

驗證命令：

```powershell
python -m compileall -q telegram_canonical_bridge tests
python -m unittest discover -s tests -v
hermes plugins doctor --ci .
hermes plugins compat .
```

## 15. 本機垂直驗收紀錄

在 Hermes 0.21.0、Windows、本機 `default` Controller 與 `operitrace-agent` worker 上已證明：

1. 一般主 Agent session 可發現並呼叫 `agent_task_start`。
2. worker 沿用既有 canonical `Bot Chat` session。
3. worker `pre_llm_call` 產生真實 `running`，明確 result 與 final 後 exit 0 完成。
4. `/agenttask status` 能讀到 worker start、final 與 exit code。
5. `agent_task_message` 保存 note，worker 透過 `bridge_task_inbox` 讀到後回覆預期 sentinel。
6. 長時間本機等待任務可由 `/agenttask cancel` tree-kill，狀態保持 `cancelled`。
7. 原生 Telegram route 實際收到任務事件。
8. 暫時積壓的多筆事件由 async delivery runner 全部送出，global native outbox 歸零，runner 自行退出。

由於目前自動化環境沒有可控制的 Telegram UI surface，視覺上的手機 client 排版仍由使用者做最後人工確認；transport delivery、Telegram message IDs 與 durable outbox 已由 Hermes 原生回傳驗證。
