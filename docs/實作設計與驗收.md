# 實作設計與驗收

## 目標與不變條件

目標不是做另一個 Telegram agent，而是讓 Telegram 成為 Hermes 主 agent 的一個安全輸入／輸出表面，同時保留主 agent 在 Bot Mode 下的 `message_agent` 能力。

本實作以四個不變條件約束設計：

1. 不建立 `agent:main:telegram:*` 或任何一般 Telegram session。
2. 只接受指定 profile 的既有 canonical session，且其標題須為精確的 `Bot Chat`。
3. Telegram update 在送往 Hermes 前先落地；assistant 回覆在送往 Telegram 前也先落地。
4. 任一端短暫斷線只會延遲，不會以重送 prompt 的方式重複執行 agent 任務。

## 架構

| 元件 | 責任 | 更新隔離方式 |
| --- | --- | --- |
| `adapter.py` | Hermes platform adapter、Telegram polling、背景 loop、鎖定 bot token | 僅使用 Hermes 公開的 `BasePlatformAdapter`、`PlatformConfig`、`register_platform()` 行為 |
| `telegram_api.py` | Telegram Bot API `getUpdates`、`sendMessage`、`sendChatAction` | 僅用 Python 標準函式庫，沒有 `python-telegram-bot` 相依 |
| `hermes_rpc.py` | `/api/ws` JSON-RPC、小生命週期 WebSocket、header 認證 | 將 RPC 協定集中在單一檔案；Hermes API 變更時只需修改此處 |
| `service.py` | 找到 canonical session、提交 prompt、補讀 history | 絕不呼叫一般平台 session 建立流程 |
| `state.py` | inbound／route／canonical history／outbox SQLite 狀態 | 所有重要跨網路動作都有可重試的資料庫紀錄 |
| `config.py` | 設定驗證、secret 讀取、路徑預設 | 將目前 Hermes 的 scoped secret helper 限縮在這一處，舊版沒有時才退回環境變數 |

### 資料流

```text
1. Telegram getUpdates
2. allowlist + private-chat 檢查
3. inbound 寫入 SQLite（update_id 唯一）
4. profiles.list → 找 profile.canonical_session
5. session.resume → prompt.submit(queued=true)
6. session.history 定期補讀 assistant 訊息
7. canonical_seen 去重，outbox 寫入 SQLite
8. Telegram sendMessage 成功後標示 sent
```

Hermes session 壓縮可能使 runtime session id 變動，因此每次 RPC 操作都重新讀 `profiles.list`，並優先使用 `canonical_session.resolved_id`，不把舊 runtime id 當成永久識別。

### 為何使用短生命週期 RPC

目前本機 Hermes 0.21.0 的多端即時事件所有權在舊版仍可能由最後一個 WebSocket 連線取得。若 bridge 常駐訂閱 canonical session，Desktop 的即時觀看端可能被影響。

因此 V1 預設每次只建立完成單一 RPC 工作所需的 WebSocket，結束即釋放；assistant 結果以 `session.history` 輪詢補讀。這犧牲了幾秒鐘即時性，換取 Desktop 與 bridge 共存，以及 server／bridge 重啟後可由持久歷史恢復。

未來 Hermes 若明確提供穩定的多 viewer event fan-out 合約，可在 `hermes_rpc.py` 增加事件串流最佳化；SQLite history 補讀仍保留作為恢復來源。

## 耐久性與去重

| 情境 | 行為 |
| --- | --- |
| Telegram 重送相同 update | `inbound.update_id` 唯一鍵拒絕重複，offset 只在安全處理後推進 |
| Hermes backend 暫時不可達（尚未送出 request） | inbound 留在 `retry`，採指數退避；第一次失敗會排入一則通知 |
| prompt.submit 送出後失去確認 | 標示 `uncertain` 且不自動重送；Hermes 目前未提供 idempotency key，重送可能讓 agent 做兩次工作。使用者可先等候回覆，或以新訊息重新提出需求 |
| bridge 在 prompt.submit 成功回覆後崩潰 | 該筆 inbound 已標為 submitted，不會盲目重送；後續 history 仍會回收結果 |
| Hermes server 重啟 | 重新 resume canonical session，從持久 `session.history` 補讀；不依賴記憶體 event buffer |
| Telegram 發送失敗 | outbox 保留並重試；每一則長回覆切段後獨立記錄，可避免已送片段全數重送 |
| 新使用者碰到已綁定 Controller | 拒絕輸入，並以 outbox 提示 V1 的單一私訊限制 |

## 安全邊界

- 預設拒絕所有 Telegram 使用者，`allowed_user_ids` 是必要設定。
- 只接受 `chat.type == private`；不提供群組或頻道的隱性入口。
- Telegram token 和 Hermes backend token 僅從 Hermes secret 範圍／環境讀取，`backend_url` 禁止含 `token=` query string；現行 Hermes loopback WebSocket 合約雖要求 handshake query credential，外掛只在記憶體中臨時附加，絕不寫回設定或日誌。
- Telegram token 以 SHA-256 衍生值取得 Hermes scoped lock，防止相同 Bot 被兩個 gateway 同時 long-poll。
- 建議 `hermes serve` 僅綁定 loopback。V1 的靜態 session-token 模式只適用於此邊界；跨機器時先以受保護的 tunnel 將 endpoint 收斂回本機，不能把 token 寫入 URL。
- SQLite state file 可能含 Telegram chat ID、使用者輸入與待回覆內容；應放在受限權限的磁碟，並納入本機備份政策。

## 相容性策略

外掛避免修改 Hermes core。主要依賴 Hermes 原生插件合約：`plugin.yaml`、`__init__.py` 的 `register(ctx)`，以及 platform registry。相依的 Hermes-specific 邊界只有兩類：

1. adapter lifecycle：`BasePlatformAdapter`、`PlatformConfig`、scoped lock。
2. backend RPC：`profiles.list`、`session.resume`、`prompt.submit`、`session.history`。

非公開 helper `gateway.platforms._shared.get_scoped_secret` 被隔離在 `config.py`，並具備舊版環境變數 fallback；其他邏輯不散落 Hermes 內部 import。每次 Hermes 升級後，先跑：

```powershell
hermes plugins doctor --ci <plugin-path>
hermes plugins compat <plugin-path>
```

## 上線驗收清單

1. 目標 profile 已存在標題完全為 `Bot Chat` 的 canonical conversation，且可在該 profile 的 Bot Mode 使用 `message_agent`。
2. `<HERMES_HOME>/.env` 已有穩定的 `HERMES_DASHBOARD_SESSION_TOKEN`，且 `TELEGRAM_CANONICAL_BRIDGE_BACKEND_TOKEN` 與其相同。
3. `hermes serve --host 127.0.0.1 --port 9119 --skip-build` 可正常啟動。
4. `hermes plugins doctor --ci <plugin-path>` 與 `hermes plugins compat <plugin-path>` 均通過。
5. `config.yaml` 啟用 `telegram-canonical-bridge` 與 `gateway.platforms.telegram_canonical_bridge`，並只設定可信任的 `allowed_user_ids`。
6. 啟動 `hermes gateway run` 後，`/help` 能回覆本機說明，`/status` 顯示 backend 狀態。
7. 從 allowlist Telegram 私訊傳送一個低風險文字，確認它出現在 canonical `Bot Chat`，且該 session 仍能呼叫 `message_agent`。
8. 讓主 agent 呼叫一個背景子 agent，確認最終 assistant 回覆在 history 補讀後回傳 Telegram。
9. 重啟 `hermes serve` 或 gateway，確認沒有重送已 submitted 的 prompt，且未送出的 Telegram outbox 最終補送。

## 已知範圍與下一版方向

- V1 僅支援一個 Telegram 私訊對一個 Controller profile；多使用者協作必須先決定權限、對話隔離與衝突策略。
- V1 僅支援文字；媒體應在後續以明確的檔案落地、掃毒／大小限制與工具權限模型處理。
- 回覆以 history polling 傳回，預設約 3 秒延遲，不是 token streaming。
- backend token 是高權限憑證。若要將 backend 暴露在網路，下一版應優先支援由 Hermes 正式發行的 service credential，而不是複用 Dashboard session token。
