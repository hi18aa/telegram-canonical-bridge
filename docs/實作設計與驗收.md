# v0.6.2 實作設計與驗收

## 1. 問題定義

Hermes 原生 Telegram 已能穩定處理「使用者 ↔ 主 Agent」。缺口只在 Telegram session 不一定擁有 canonical `Bot Chat` 才會注入的內建 `message_agent`，因此主 Agent 難以可靠派工給專門 Bot。

本外掛的唯一責任是提供「主 Agent ↔ Bot」sidecar；不得取代原生 Telegram。

## 2. 架構

```text
Telegram 使用者
    ↕ Hermes 原生 Telegram
Controller Agent
    ↕ agent_task_start / status / message / cancel
SQLite task ledger + background process handle
    ↘ exact payload：content-addressed UTF-8 artifact + SHA-256 manifest
    ↕ 公開 hermes chat CLI
TCB Task <TASK_ID>（每個 task 獨立 conversation）
    ↕ bridge_task_update / inbox / status + lifecycle hooks
Worker Bot profile

任務事件
    → durable outbox
    → 公開 hermes send
    → Hermes 原生 Telegram
```

`agent_task_start` 是缺少內建 `message_agent` 的 surface 所使用的穩定派工介面。它不註冊同名工具、不包裝核心實作，也不依賴 Desktop 私有 RPC。

## 3. 關鍵決策

### 3.1 每個 task 一個隔離 conversation

runner 使用：

```text
hermes -p <target> chat --in ~ -c "TCB Task <TASK_ID>" --create-if-missing --source tool -Q --query-file <path>
```

不用 canonical `Bot Chat` 的原因：該 session 若正在 Desktop 開啟，CLI 可能只能得到 queue acknowledgement，卻沒有新 Bot turn。task 專屬名稱保證正常情況下沒有其他 live owner，也阻止不同 Controller／task 混用上下文。

### 3.2 同一 worker 序列化

每個 target profile 有一把跨程序 OS file lock。相同 worker 的 task 依序執行，不同 workers 可並行。這是資源隔離，不是 session 共用。

### 3.3 真實狀態，不推測

```text
dispatching → dispatched → running → returning → completed
                         ↘ waiting / blocked
任何未確認路徑          → unconfirmed / failed / cancelled
```

- `dispatched`：只有背景 process ID。
- `running`：目標 profile 的 `pre_llm_call` 或可辨識工具活動。
- `returning`：worker 的 `post_llm_call`。
- `completed`：final evidence 與 runner completion 已收斂，或 runner 有可辨識 final output。
- `unconfirmed`：runner 結束但缺少 final evidence；可以被較晚的確切證據修正。

已確認的 `completed`、`failed`、`cancelled` 不接受較晚 observer 降級。runner 結束時會直接收斂共用 ledger；來源 session 收到的 completion notification 會用同一套規則再次確認，因此 Controller 暫時離線不會讓 task 永遠停在 `returning`。

### 3.4 新訊息不是 interrupt

`agent_task_message` 只寫入 `task_notes`。Worker 在開始、自然里程碑與 final 前呼叫 `bridge_task_inbox`。若留言在 final 後才到達，ledger 會標示 missed 並通知使用者。

`agent_task_cancel` 才是明確 interrupt；它用 Hermes `process_manage` 終止 runner 與子程序樹。取消不回滾已完成的外部副作用。

### 3.5 事件不編輯舊訊息

每次有真正狀態變更，ledger 新增 immutable event。outbox 逐 task 保序，以短生命週期 delivery runner 呼叫：

```text
hermes -p <origin-controller-profile> send --to <delivery_target> --file <path> --json
```

即使 runner 是由 worker hook 啟動，也必須明確指定來源 Controller profile，避免繼承 worker 的 profile。暫時失敗採 exponential backoff，正常 Controller turn 會再次喚醒 pending outbox；外掛本身不接觸 Telegram Bot API。

### 3.6 逐字資料面與控制面分離

`agent_task_start.exact_payload.text` 是唯一逐字資料面。Bridge 不做 `strip`、換行正規化或字元替換，而是直接編碼為 UTF-8 bytes，寫入 content-addressed artifact，並建立包含路徑、byte length 與 SHA-256 的 manifest。task-specific binding 只用來讓 `agent_task_status` 回讀並重新驗證契約。

Worker handoff 不包含 exact body，只包含 artifact／manifest 路徑、digest 與 Controller 的操作摘要。task marker、`bridge_task_update`、`bridge_task_inbox` 及 completion 規則屬於控制面，放在摘要之前；worker `pre_llm_call` 只做 task 綁定，不再注入逐 task 指引。這使模型即使看見控制文字，也不能把它當成 exact body 的尾端；對外資料必須直接取自已驗證 artifact。

Native `message_agent` 不受影響。只有透過 bridge 且內容需逐字對外使用時，Controller 才需要提供 `exact_payload`；使用者不需要手動管理檔案。

## 4. 公開工具契約

### Controller

| 工具 | 必要輸入 | 主要輸出／語意 |
|---|---|---|
| `agent_task_start` | `target`, `message`; `attachments`、`exact_payload` 選填 | `task_id`, `process_id`, `sent`; exact payload 回傳 artifact/digest/verified；sent 不代表開始或完成 |
| `agent_task_status` | `task_id` 選填 | evidence-backed task snapshot |
| `agent_task_message` | `task_id`, `message` | durable note；不即時中斷 |
| `agent_task_cancel` | `task_id` | 先保存 `stopping`；只有 runner／程序管理確認後才是 `cancelled` |

### Worker

| 工具 | 必要輸入 | 主要輸出／語意 |
|---|---|---|
| `bridge_task_update` | `task_id`, `status`, `message` | 可公開的 progress/result |
| `bridge_task_inbox` | `task_id` | 未讀補充指示 |
| `bridge_task_status` | `task_id` 選填 | ledger snapshot |

只有 task 指定的 profile，且 session 已由 marker 綁定，才能更新或讀取該 worker task。marker 本身不是跨 profile 授權。

## 5. 儲存模型

新版資料庫：

```text
<HERMES_ROOT>/plugin-data/telegram-canonical-bridge/tasks.sqlite3
```

僅有四個應用表：

- `tasks`
- `task_events`
- `task_notes`
- `outbox`

不含 Telegram inbound、chat route、message card、canonical history、Desktop RPC 或 token。

舊 `bridge.sqlite3` 不遷移、不讀取，避免重播 legacy inbound／outbox。管理者完成外部副作用稽核後再自行備份或刪除。

逐字 artifact 不寫入 SQLite，位置如下：

```text
<HERMES_ROOT>/plugin-data/telegram-canonical-bridge/exact-payloads/
  blobs/sha256/<SHA256>/body.utf8.txt
  blobs/sha256/<SHA256>/manifest.json
  bindings/<TASK_ID>.json
```

`body.utf8.txt` 只含 caller 提供的 bytes；manifest 與 binding 不保存正文，也不含 task 控制指引。

## 6. 失敗模型

- profile 不存在或未列 roster：建立 `failed` event，不 spawn。
- background tool 沒有 process ID：`failed`。
- provider auth／quota／rate limit／server error：從 runner completion 分類為 `failed`。
- exit 0 但沒有 hook 或可辨識 final：`unconfirmed`，不得宣稱成功。
- task conversation 被人為開啟造成 live owner：`failed: target_busy`。
- delivery 失敗：task 狀態不倒退，outbox 保留並重試。
- Controller 重複執行同一 tool call：以 `(origin_session_id, origin_tool_call_id)` 冪等，不重複 spawn。

## 7. 產品邊界

禁止：

- `register_platform`
- Telegram `getUpdates`、`sendMessage` 或 token 管理
- 第二個 Telegram poller
- Desktop WebSocket RPC／`session.resume`
- Hermes core patch／內建 `message_agent` override
- 反覆編輯同一 Telegram 狀態訊息
- 不明外部結果的自動重派

## 8. 驗收命令

```powershell
rg -n "register_platform|getUpdates|sendMessage|session.resume|TELEGRAM_CANONICAL_BRIDGE_BOT_TOKEN" .
python -m compileall -q telegram_canonical_bridge tests
python -m unittest discover -s tests -v
hermes plugins doctor --ci .
hermes plugins compat .
```

`rg` 只能命中文件中的禁止項目說明或測試斷言，不得命中產品實作。

## 9. 真實 artifact E2E

發布前必須用同一 commit：

1. 安裝並啟用 Controller plugin。
2. 安裝並啟用至少一個 worker profile plugin。
3. Doctor 顯示 general plugin、7 tools、5 hooks、0 platform。
4. 從正式 Hermes 入口建立一個無外部副作用 task。
5. `tasks.sqlite3` 依序出現 `dispatched`、`running`、`returning`、`completed`。
6. Worker session title 是 `TCB Task <TASK_ID>`，不是 `Bot Chat`。
7. Telegram 收到新的任務事件，outbox 最終歸零。
8. 重複同一 tool call 不會 spawn 第二個 runner。
9. exact payload probe 的 worker 回讀 bytes、byte length 與 SHA-256 全部相符，且未啟動任何網站 workflow 或其他外部副作用。

缺少任一證據不得發布。
