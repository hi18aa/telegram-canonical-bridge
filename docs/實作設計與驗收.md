# v0.6.5 實作設計與驗收

## 1. 問題定義

Hermes 原生 Telegram 已能穩定處理「使用者 ↔ 主 Agent」。缺口只在 Telegram session 不一定擁有 canonical `Bot Chat` 才會注入的內建 `message_agent`，因此主 Agent 難以可靠派工給專門 Bot。

本外掛的唯一責任是提供「主 Agent ↔ Bot」sidecar；不得取代原生 Telegram。

## 2. 架構

```text
Telegram 使用者
    ↕ Hermes 原生 Telegram
Controller Agent
    ↕ agent_task_start / status / message / cancel
SQLite task ledger + background process handle
    ↘ exact payload：content-addressed UTF-8 artifact + SHA-256 manifest
    ↕ 公開 hermes chat CLI
TCB Task <TASK_ID>（每個 task 獨立 conversation）
    ↕ bridge_task_update / inbox / status + lifecycle hooks
Worker Bot profile

任務事件
    → durable outbox
    → 公開 hermes send
    → Hermes 原生 Telegram
```

`agent_task_start` 是缺少內建 `message_agent` 的 surface 所使用的穩定派工介面。它不註冊同名工具、不包裝核心實作，也不依賴 Desktop 私有 RPC。

## 3. 關鍵決策

### 3.1 每個 task 一個隔離 conversation

runner 使用：

```text
hermes -p <target> chat --in ~ -c "TCB Task <TASK_ID>" --create-if-missing --source tool -Q --query-file <path>
```

不用 canonical `Bot Chat` 的原因：該 session 若正在 Desktop 開啟，CLI 可能只能得到 queue acknowledgement，卻沒有新 Bot turn。task 專屬名稱保證正常情況下沒有其他 live owner，也阻止不同 Controller／task 混用上下文。

### 3.2 同一 worker 序列化

每個 target profile 有一把跨程序 OS file lock。相同 worker 的 task 依序執行，不同 workers 可並行。這是資源隔離，不是 session 共用。

### 3.3 真實狀態，不推測

```text
dispatching → dispatched → running → returning → completed
                         ↘ waiting / blocked
                         ↘ settling → interrupted ─┐
無 final 的 exit 0                    unconfirmed ─┴→ 明確 agent_task_message
                                                       → continuing → running
worker 啟動前的確定失敗              failed / cancelled
```

- `dispatched`：只有背景 process ID。
- `running`：目標 profile 的 `pre_llm_call` 或可辨識工具活動。
- `returning`：worker 的 `post_llm_call`。
- `completed`：final evidence 與 runner completion 已收斂，或 runner 有可辨識 final output。
- `settling`：worker hook 已看到 abnormal turn end，但 OS runner 尚未回報 exit；不可啟動 continuation。
- `continuing`：Main 已明確要求接續，bridge 已 claim 同一 task 並正在建立／等待 continuation turn；仍不是 Bot 已開始的證據。
- `interrupted`：worker 已開始、runner 非零結束且沒有 final evidence；可能已有外部副作用，可安全接續同一 task 做查詢／修復／reconcile。
- `unconfirmed`：runner exit 0 但缺少 final evidence；可以被較晚的確切證據修正，也可明確接續同一 task 查證。

公開 snapshot 另提供 `lifecycle=active|settling|resumable|terminated`、`resumable` 與 `final`，讓 Main 不必從自然語言猜測。已確認的 `completed`、worker 啟動前 `failed`、`cancelled` 不接受較晚 observer 降級；`interrupted` 與 `unconfirmed` 是沒有 live runner 的可接續終態。v0.6.4 已留下、具有 worker session 且沒有 final 證據的 `failed` 紀錄不改寫資料列，但公開為 `resumable=true`、`final=false`；仍須 Main 明確送出 `agent_task_message` 才會 claim continuation。runner 結束時會直接收斂共用 ledger；來源 session 收到的 completion notification 會用同一套規則再次確認，因此 Controller 暫時離線不會讓 task 永遠停在 `returning`。

### 3.4 新訊息不是 interrupt

active task 的 `agent_task_message` 只寫入 `task_notes`。Worker 在開始、自然里程碑與 final 前呼叫 `bridge_task_inbox`。若留言在真正結案或 final 後才到達，ledger 會標示 missed 並通知使用者。

`interrupted`／`unconfirmed` task 收到明確 `agent_task_message` 時，ledger 先用 compare-and-set claim 一次 continuation，再啟動：

```text
hermes -p <target> chat --in ~ -c "TCB Task <TASK_ID>" --source tool -Q --query-file <control>
```

接續命令不帶 `--create-if-missing`，因此只能進入既有 conversation。其 query file 只要求 worker 讀取 `bridge_task_inbox`，不含原始 task message、exact payload 正文或新的副作用授權。多個 caller 競爭時只有一個 claim 能 spawn；新 runner 建立前會移除上一個 process identity，較晚抵達的舊 completion notification 無法污染新 runner。Bridge 不會因中斷自行觸發這條路徑。

`agent_task_cancel` 才是明確 interrupt；它用 Hermes `process_manage` 終止 runner 與子程序樹。取消不回滾已完成的外部副作用。

### 3.5 Bridge、Main 與專門 Bot 的責任切分

- Bridge：保存 lifecycle、序列化 profile、提供 inbox、以同一 task conversation 做顯式 continuation，並禁止自動 replay。
- Main：先查 `agent_task_status`；active 時補充、settling 時等待、resumable 時傳入只查詢／修復／reconcile 的 `agent_task_message`，terminated 時停止自動處理。
- 專門 Bot／OperiTrace：自行啟動或恢復瀏覽器、處理系統視窗遮擋、理解 transaction／dispatch 狀態並執行 site-specific reconciliation。

Facebook、Threads、selector、browser UI 或網站 Workflow 規則不得進入 Bridge。若專門 Bot 不會恢復瀏覽器或查詢既有 transaction，應修改該 Bot 的 SOUL／技能，而不是擴張 Bridge。

Bridge 的 at-most-once 邊界是「相同初次 tool call 不重複建立 runner、同一 continuation claim 只建立一個 runner、原始 task payload 不重送」。網站 dispatch／transaction 是否已提交，只能由專門 Bot 與 OperiTrace 的既有證據判定；Bridge 不會假裝能以通用 ledger 保證網站端冪等。

### 3.6 事件不編輯舊訊息

每次有真正狀態變更，ledger 新增 immutable event。outbox 逐 task 保序，以短生命週期 delivery runner 呼叫：

```text
hermes -p <origin-controller-profile> send --to <delivery_target> --file <path> --json
```

即使 runner 是由 worker hook 啟動，也必須明確指定來源 Controller profile，避免繼承 worker 的 profile。暫時失敗採 exponential backoff，正常 Controller turn 會再次喚醒 pending outbox；外掛本身不接觸 Telegram Bot API。

### 3.7 逐字資料面與控制面分離

`agent_task_start.exact_payload.text` 是唯一逐字資料面。Bridge 不做 `strip`、換行正規化或字元替換，而是直接編碼為 UTF-8 bytes，寫入 content-addressed artifact，並建立包含路徑、byte length 與 SHA-256 的 manifest。task-specific binding 只用來讓 `agent_task_status` 回讀並重新驗證契約。Runner 會再次驗證 binding，再把 artifact path、SHA-256 與 byte length 以 task-local 環境變數交給 Worker；不傳正文，且沒有 payload 時清除同名舊值。

Worker handoff 不包含 exact body，只包含 artifact／manifest 路徑、digest 與 Controller 的操作摘要。task marker、`bridge_task_update`、`bridge_task_inbox` 及 completion 規則屬於控制面，放在摘要之前；worker `pre_llm_call` 只做 task 綁定，不再注入逐 task 指引。普通 Controller turn 也不再由 hook 回傳動態派工文字，該說明只存在正式 system prompt section，不能被接到 user message 尾端。這使模型即使看見控制文字，也不能把它當成 exact body 的尾端；對外資料必須直接取自已驗證 artifact。

Native `message_agent` 不受影響。只有透過 bridge 且內容需逐字對外使用時，Controller 才需要提供 `exact_payload`；使用者不需要手動管理檔案。

## 4. 公開工具契約

### Controller

| 工具 | 必要輸入 | 主要輸出／語意 |
|---|---|---|
| `agent_task_start` | `target`, `message`; `attachments`、`exact_payload` 選填 | `task_id`, `process_id`, `sent`; exact payload 回傳 artifact/digest/verified；sent 不代表開始或完成 |
| `agent_task_status` | `task_id` 選填 | evidence-backed snapshot，含 lifecycle／resumable／final |
| `agent_task_message` | `task_id`, `message` | active：durable note；resumable：claim 並啟動同 task continuation；不重送原任務 |
| `agent_task_cancel` | `task_id` | 先保存 `stopping`；只有 runner／程序管理確認後才是 `cancelled` |

### Worker

| 工具 | 必要輸入 | 主要輸出／語意 |
|---|---|---|
| `bridge_task_update` | `task_id`, `status`, `message` | 可公開的 progress/result |
| `bridge_task_inbox` | `task_id` | 未讀補充指示 |
| `bridge_task_status` | `task_id` 選填 | ledger snapshot |

只有 task 指定的 profile，且 session 已由 marker 綁定，才能更新或讀取該 worker task。marker 本身不是跨 profile 授權。

## 5. 儲存模型

新版資料庫：

```text
<HERMES_ROOT>/plugin-data/telegram-canonical-bridge/tasks.sqlite3
```

僅有四個應用表：

- `tasks`
- `task_events`
- `task_notes`
- `outbox`

v0.6.5 沒有新增或改寫資料表；continuation 只使用既有 task status、event、note 與 process identity，因此可直接讀取 v0.6.4 ledger，不需要資料遷移或 replay。舊版已啟動 worker、無 final 的 `failed` 只在讀取時分類為 resumable；不會因啟動 plugin 而修改 task 或產生 runner。

不含 Telegram inbound、chat route、message card、canonical history、Desktop RPC 或 token。

舊 `bridge.sqlite3` 不遷移、不讀取，避免重播 legacy inbound／outbox。管理者完成外部副作用稽核後再自行備份或刪除。

逐字 artifact 不寫入 SQLite，位置如下：

```text
<HERMES_ROOT>/plugin-data/telegram-canonical-bridge/exact-payloads/
  blobs/sha256/<SHA256>/body.utf8.txt
  blobs/sha256/<SHA256>/manifest.json
  bindings/<TASK_ID>.json
```

`body.utf8.txt` 只含 caller 提供的 bytes；manifest 與 binding 不保存正文，也不含 task 控制指引。

## 6. 失敗模型

- profile 不存在或未列 roster：建立 `failed` event，不 spawn。
- background tool 沒有 process ID：`failed`。
- 初次派工在 worker 尚未啟動時的 provider／設定／target failure：`failed`。
- continuation 在新 worker turn 前失敗：回到 `interrupted/resumable`，保留原 task 與 inbox；不自動 retry。
- worker 已啟動後因 provider、執行預算或未知 runner error 非零結束：`interrupted/resumable`；外部結果保持未知，禁止自動 replay。
- exit 0 但沒有 hook 或可辨識 final：`unconfirmed/resumable`，不得宣稱成功。
- 初次派工的 task conversation 已有 live owner：worker 尚未啟動，`failed: target_busy`；continuation 遇到相同情形則保持原 task `interrupted/resumable`，不另建 conversation。
- delivery 失敗：task 狀態不倒退，outbox 保留並重試。
- Controller 重複執行同一 tool call：以 `(origin_session_id, origin_tool_call_id)` 冪等，不重複 spawn。
- 多個 continuation request：以 task status CAS，只建立一個 runner；其他留言留在同一 inbox。

## 7. 產品邊界

禁止：

- `register_platform`
- Telegram `getUpdates`、`sendMessage` 或 token 管理
- 第二個 Telegram poller
- Desktop WebSocket RPC／`session.resume`
- Hermes core patch／內建 `message_agent` override
- 反覆編輯同一 Telegram 狀態訊息
- 不明外部結果的自動重派

## 8. 驗收命令

```powershell
rg -n "register_platform|getUpdates|sendMessage|session.resume|TELEGRAM_CANONICAL_BRIDGE_BOT_TOKEN" .
python -m compileall -q telegram_canonical_bridge tests
python -m unittest discover -s tests -v
hermes plugins doctor --ci .
hermes plugins compat .
```

`rg` 只能命中文件中的禁止項目說明或測試斷言，不得命中產品實作。

## 9. 真實 artifact E2E

發布前必須用同一 commit：

1. 安裝並啟用 Controller plugin。
2. 安裝並啟用至少一個 worker profile plugin。
3. Doctor 顯示 general plugin、7 tools、5 hooks、0 platform。
4. 從正式 Hermes 入口建立一個無外部副作用 task。
5. 正常路徑的 `tasks.sqlite3` 依序出現 `dispatched`、`running`、`returning`、`completed`。
6. Worker session title 是 `TCB Task <TASK_ID>`，不是 `Bot Chat`。
7. Telegram 收到新的任務事件，outbox 最終歸零。
8. 重複同一 tool call 不會 spawn 第二個 runner。
9. exact payload probe 的 worker 回讀 bytes、byte length 與 SHA-256 全部相符，且未啟動任何網站 workflow 或其他外部副作用。
10. synthetic interruption 依序為 `settling`、`interrupted/resumable`；沒有自動 spawn。明確 `agent_task_message` 只建立一個同 task continuation，命令不含 `--create-if-missing`，handoff 不含原始任務或 exact body。

缺少任一證據不得發布。
